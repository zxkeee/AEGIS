# AEGIS от А до Я — простыми словами, для себя

> Личный справочник, не для показа партнёрам/грантовым комиссиям (для этого
> есть отдельные документы — см. низ файла). Задача этого документа — чтобы
> ты сам понимал продукт целиком, без пробелов. Написано человеческим языком,
> без маркетинга. Проверено по коду, не с чужих слов — где я не проверял
> лично, это отмечено прямо в тексте.

## 1. Что это и зачем

**AEGIS — программа, которая встаёт между интернетом и твоими API** (API —
это то, через что твой сайт/приложение общается с сервером: "дай мне заказы
пользователя", "сохрани платёж" и т.д.). Весь трафик идёт не напрямую к
твоим серверам, а сначала через AEGIS — он смотрит на каждый запрос, решает
"пропустить или заблокировать", и попутно записывает, что вообще происходит.

**Зачем это нужно.** У любой компании с API есть пять типовых проблем:

1. **Забытые API.** Разработчики выкатывают новые эндпоинты быстрее, чем
   кто-то успевает их задокументировать. Забытые ("теневые") и устаревшие, но
   всё ещё работающие ("зомби") API — частая причина утечек, потому что их
   никто не проверяет.
2. **Разнобой в защите.** Одна команда поставила аутентификацию, другая —
   нет. Никто не знает общую картину: что вообще защищено.
3. **Нет видимости "кто ходит куда".** Обычно нельзя быстро ответить на
   вопрос "кто вызывает этот эндпоинт и как часто" — данные размазаны по
   логам разных сервисов.
4. **Утечка данных в ответах.** API отдают персональные данные, номера карт
   и т.д. незаметно, пока кто-то не сообщит об этом снаружи (обычно после
   того, как уже поздно).
5. **Автоматизированные атаки.** Перебор паролей, скрапинг, перебор ID
   объектов, DDoS-подобные всплески — идут постоянно.

AEGIS решает это тем, что становится **единой точкой**, через которую видно
и контролируется весь трафик.

## 2. В чём отличие от "просто ещё одного файрвола"

Обычно это три разных продукта от трёх разных вендоров:

- **API Gateway** — прокси, балансировка нагрузки, маршрутизация.
- **WAAP** (Web App & API Protection) — файрвол, rate-limit, антибот, DLP,
  проверка личности.
- **ASPM** (API Security Posture Management) — каталог API, оценка риска,
  аналитика "кто ходит куда".

**AEGIS — это все три в одном бинарнике.** Одна установка вместо трёх
интеграций.

Но настоящее отличие не в том, что "у нас тоже есть файрвол" — файрвол есть
у всех. Отличие в том, что AEGIS с первого дня **строит карту твоего API и
граф "кто к чему ходит"** — и на этой карте уже стоит детект утечек объектов
(BOLA, подробно — в разделе 6). У большинства конкурентов уровня "просто
файрвол" такой карты вообще нет — а без неё эта фича невозможна.

## 3. Как физически всё устроено

**Один процесс, два порта.**

- **Порт 8080 (data plane)** — сюда идёт реальный трафик клиентов.
- **Порт 8081 (admin plane)** — сюда идёшь ты: дашборд, управление, метрики.

Разделены специально: если данные-плейн под атакой или перегружен, у тебя
всё равно остаётся доступ к управлению через отдельный порт.

**Хранилища:**
- **Redis** — всё быстрое и недолгоживущее: счётчики лимитов, чёрные списки
  IP, поведенческие баллы, сессии админки.
- **PostgreSQL** (не обязателен) — каталог API и журнал форензики (кто что
  когда сделал/попытался). Если Postgres не настроен — AEGIS просто не ведёт
  каталог, всё остальное работает как обычно.

**Конфиг меняется на лету.** Поменял правило в YAML-файле — оно применяется
без перезапуска и без обрыва текущих соединений (называется hot-reload).

## 4. Путь одного запроса — по шагам, в реальном порядке

Это важно: раньше в черновиках (и в моих же более ранних объяснениях тебе)
порядок был **неправильно упрощён** — я говорил "сначала проверяем личность".
Это ошибка. Реальный порядок (проверено напрямую по файлу
`internal/gateway/chain.go`) такой:

**Шаг 1 — "Это вообще похоже на атаку?"** (до проверки личности)
Сначала проверяется репутация IP, ограничение скорости запросов (rate-limit),
похоже ли это на бота, и сигнатурный файрвол (WAF) — ищет типовые паттерны
взлома в самом запросе (SQL-инъекции и т.п.).

**Шаг 2 — Запись в каталог**
Если запрос прошёл шаг 1 — событие пишется в каталог API. **Важный нюанс**:
если запрос был заблокирован на шаге 1 (атака, спам-бот, найден
SQL-инъекция) — он **не попадает в каталог вообще**. Это специально: чтобы
шум от атак не засорял карту твоего реального API. Это тоже я перепроверял
отдельно — раньше писал "каждый запрос пишется, даже заблокированный", это
было неточно.

**Шаг 3 — "Кто это, и что ему разрешено?"**
Только тут проверяется токен доступа (JWT), затем — соответствует ли запрос
документированной схеме API (защита от "лишних полей" в запросе), затем —
проверка на злоупотребление правами (BOLA/BFLA, детально в разделе 6).

**Шаг 4 — "Ничего лишнего не утекает, и ведёт себя нормально?"**
DLP проверяет ответ на утечку чувствительных данных (номера карт, email и
т.п.) и, если нужно, маскирует их. Отдельно — поведенческий анализ: копится
профиль поведения этого клиента во времени, и если он резко меняется —
это сигнал.

**Итог:** прошёл все шаги — запрос доходит до твоего реального сервера.
Не прошёл — уходит в "заблокировано", и твой сервер его вообще не видит.

## 5. Мультитенантность (если у тебя несколько клиентов на одной установке)

Если один AEGIS обслуживает несколько разных компаний-клиентов одновременно
— их данные строго изолированы: каждый ключ в Redis и каждая строка в
Postgres привязаны к конкретному клиенту (tenant), и есть **дополнительный
предохранитель на уровне самой базы данных** (Row-Level Security) — то есть
даже если разработчик где-то забудет добавить фильтр "только для этого
клиента", база физически не отдаст чужие строки. Это реально сделано (я
проверял код: `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` в
`internal/discovery/store_pg.go` и `internal/forensic/pg_sink.go`), не
просто задокументировано.

## 6. Флагманская фича — детект утечки чужих данных (BOLA/BFLA)

Это то, чем AEGIS реально отличается, поэтому разберём подробно.

**Проблема, которую это решает:** классический баг в API — когда пользователь
меняет число в адресе (`/orders/1001` → `/orders/1002`) и видит чужой заказ,
потому что сервер не проверил "а этот заказ точно принадлежит тебе?". Это
называется BOLA/IDOR, и сигнатурный файрвол **физически не может** это
поймать — запрос выглядит абсолютно нормально, ничего "вредоносного" в нём
нет.

**Как AEGIS это ловит — два разных механизма:**

1. **Перебор (enumeration).** Если один и тот же клиент за короткое время
   обращается к аномально большому числу разных ID — это подозрительно.
   AEGIS не просто ставит фиксированный порог, а **учится норме конкретного
   клиента** (у одного нормально 5 запросов в минуту, у другого — 60, оба не
   должны триггерить друг на друга) и триггерит только на аномальное
   отклонение от **личной** нормы.

2. **Разовая утечка одного объекта (сложнее и ценнее).** Это когда клиент
   один раз обратился к чужому объекту — без перебора, без паттерна. Это
   AEGIS ловит через **пассивное обучение владению**: смотрит, кто обычно
   обращается к какому объекту, и если видит успешный (код 2xx, не 403/404)
   доступ клиента к объекту, который до этого трогал кто-то другой — это
   флагуется. Если дополнительно настроено `owner_fields` (сказать AEGIS,
   в каком поле ответа лежит "настоящий владелец") — это превращается из
   догадки в **подтверждённый** факт утечки, и AEGIS может **заблокировать
   такой запрос ещё до того, как он дойдёт до твоего сервера**, а не просто
   записать это в лог постфактум.

**Честная деталь:** без настроенного `owner_fields` это работает как
эвристика (уровень серьёзности "warning"), не как подтверждённый факт. Это
не недостаток — это как оно спроектировано, но об этом важно знать, если
будешь кому-то это объяснять.

Всё это реально в коде — я лично прочитал файл `internal/middleware/abuse.go`
целиком и проверил, что под каждый сценарий есть тест (28 тестов), включая
конкретно проверку "владение, выученное на чтении, защищает и от записи/
удаления" — не только теоретически заявлено.

## 7. Что происходит, когда что-то ломается

**Упал Redis** (хранилище лимитов/блок-листов) — AEGIS не падает. По
умолчанию просто пропускает трафик (fail-open), либо можно настроить
блокировать всё (fail-closed) — это выбор оператора для каждого конкретного
контроля. Проверено на живом стенде под нагрузкой: при полностью убитом
Redis — **100% запросов успешны**, просто задержка выросла с обычных
десятков миллисекунд до p99 864мс.

**Упал Postgres** (каталог/журнал) — трафик клиентов вообще не замечает
этого, потому что запись в каталог идёт асинхронно, в стороне от основного
пути запроса. Тоже проверено на живом стенде: 100% успех, задержка ровная.

**Упал сам процесс AEGIS:**
- Если это **одна копия** (обычная ситуация для первого пилота/демо) —
  трафик клиента **полностью останавливается**, потому что AEGIS стоит
  "инлайн" (в самом пути трафика), а не сбоку. Это реальный риск, не
  теоретический.
- Если это **несколько копий за балансировщиком** (продакшн-развёртывание в
  Kubernetes) — упавшая копия сама выпадает из ротации, остальные продолжают
  работать. Но это работает только если заранее заложен запас мощности
  (минимум +1 копия сверх необходимого).

## 8. Как это ставится у клиента

**Упаковка:** один Docker-образ. Дальше — выбор способа запуска:
- **Docker Compose** — один сервер, для демо/пилота. Просто, но одна копия
  (см. риск выше).
- **Kubernetes + Helm chart** — несколько копий, автомасштабирование, для
  реального продакшна.

**Как разворачивается поэтапно (чтобы пилот не мог сломать клиенту прод):**

1. **Observe** — стоит перед сервисом, ничего не блокирует, только смотрит и
   записывает. В этом режиме AEGIS физически не может сломать трафик клиента
   — WAF в режиме "только замечать", авторизация не требуется жёстко, DLP
   классифицирует, но не редактирует. Это то, что делает возможным холодный
   питч потенциальному пилоту: "поставим на 2 недели, ничего не сломаем,
   покажем отчёт".
2. **Tuning** — по собранным данным убираем ложные срабатывания.
3. **Enforcement** — включаем реальную блокировку.
4. **Expansion** — раскатываем на остальные сервисы клиента.
5. **Steady state** — дальше живём по отчёту: закрываем то, что осталось
   незащищённым.

## 9. Реальное состояние продукта — честно, без прикрас

### Что уже сильно (проверено, не заявлено)
- Каталог API + граф "кто к чему ходит" — редкий фундамент для этой стадии.
- BOLA/BFLA с подтверждённым владением объекта (раздел 6).
- Мультитенантность закрыта полностью, с предохранителем на уровне БД.
- Осознанные решения про fail-open/fail-closed — не забытый угол, а
  задокументированный компромисс.
- Отказоустойчивость реально прогнана на живых отказах, не только
  заявлена.
- Есть безопасный ("Observe") режим для первого захода к клиенту без риска.

### Что честно ещё не готово

**Технически:**
- Нет независимого pentest'а (только собственные сканы).
- Нет цифры производительности на серьёзном железе (текущая — с ноутбука
  2015 года, сам продукт называет это "полом", не потолком).
- Нет out-of-band режима (только "в разрыв" трафика — inline).
- SSO — только один протокол (OIDC), без SAML/SCIM/MFA.
- SIEM-интеграция — только вебхук, без готовых коннекторов к Splunk/Elastic.

**По бизнесу:**
- Нет системы тарифов/лицензирования — физически нельзя продать с ценником
  прямо сейчас.
- Не решено, какая модель поставки: self-hosted для малого бизнеса или
  managed SaaS.
- Нет сертификации SOC2/ISO (это процесс на месяцы, не код).

## 10. Где сейчас продукт в контексте бизнеса (гранты, пилот)

Коротко, без повторения всей истории поиска (она есть в отдельных файлах,
см. низ документа):

- Проверял три военных грантовых программы (NATO DIANA, UNITE–Brave NATO,
  украинский Brave1) — все три **не подходят** AEGIS: либо юридический
  барьер по владению, либо программа заточена под физическое оружие, а не
  софт. Первоисточники прочитаны и процитированы в соответствующих файлах.
- Нашёл рабочий вариант — **EIC Accelerator** (грант ЕС именно под
  кибербезопасность, без проблемы с гражданством владельца). Основной
  открытый вопрос — нужен хотя бы один живой пилот с реальным трафиком,
  чтобы честно доказать зрелость продукта (TRL6).
- Сейчас в поиске первого пилота — вертикаль ещё не выбрана окончательно.

## 11. Мини-словарь (чтобы не гуглить на ходу)

- **Reverse proxy** — сервер, который стоит перед твоими настоящими
  серверами и принимает трафик вместо них.
- **WAF** — файрвол уровня приложения, ищет известные атаки в запросе.
- **DLP** — предотвращение утечки данных, проверяет ответы.
- **BOLA/BFLA/IDOR** — когда пользователь получает доступ к чужим данным/
  функциям просто поменяв ID или URL.
- **JWT** — подписанный токен, которым клиент доказывает, кто он.
- **Мультитенантность** — безопасная работа с несколькими клиентами на одной
  системе, с изоляцией их данных.
- **Fail-open / fail-closed** — что происходит при аварии: пропускать всё
  (открыто) или блокировать всё (закрыто).
- **Inline / out-of-band** — трафик физически идёт через инструмент, или
  инструмент только смотрит на копию.
- **TRL** — Technology Readiness Level, шкала "насколько технология реально
  проверена", от идеи (TRL1) до боевого применения (TRL9).
