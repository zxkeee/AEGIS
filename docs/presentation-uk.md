# AEGIS — Зміст презентації (українською)

> Чорновик змісту без візуального стилю — стиль буде застосовано, коли
> з'явиться референс. Структура: проблема, чому саме ми, як це працює,
> архітектура, як впроваджується.

## Яку проблему вирішуємо

Сучасні компанії мають велику і постійно змінювану поверхню API. Її складно
захищати з кількох структурних причин:

- **Забуті API.** Розробники випускають ендпоінти швидше, ніж їх встигають
  задокументувати. Забуті й застарілі, але досі доступні ендпоінти — частая
  причина витоків, бо за ними ніхто не стежить.
- **Різний рівень захисту.** Кожна команда налаштовує авторизацію та ліміти
  по-своєму. Немає єдиної картини, що взагалі захищено.
- **Немає видимості "хто до чого звертається".** На питання "хто викликає
  цей API і як часто" зазвичай немає швидкої відповіді — дані розкидані по
  логах десятків сервісів.
- **Витік даних у відповідях.** Персональні та платіжні дані витікають у
  відповідях API непомітно — поки хтось не повідомить про це ззовні.

## Чому саме ми

Зазвичай це три різні продукти від трьох різних вендорів: **API Gateway**
(проксі, балансування), **WAAP** (файрвол, ліміти, антибот, захист від
витоку даних, перевірка особи) та **ASPM** (каталог API, оцінка ризику,
аналітика). AEGIS — усе це в одному продукті: одне встановлення замість
трьох інтеграцій.

Головна відмінність — не файрвол, сигнатурний файрвол є у всіх. AEGIS з
першого дня будує **каталог API та граф "хто до чого звертається"** — і на
цьому фундаменті вже стоїть детект витоку чужих даних (розділ нижче).
У більшості конкурентів рівня "просто файрвол" такого фундаменту немає
взагалі.

AEGIS також **self-hosted, без обов'язкової хмари**: єдині зовнішні
залежності — Redis і PostgreSQL, інфраструктура, яка майже напевно вже є у
компанії. Нічого не "телефонує додому" у зовнішній сервіс.

## Як це працює

AEGIS стоїть перед API як пропускний пункт: пропускає легітимний трафік,
відсіює шкідливий, записує все по дорозі.

Запит проходить чотири перевірки по порядку:

1. **Швидкість і репутація** — чи це автоматизована атака? (репутація IP,
   ліміти швидкості, детект ботів.)
2. **Що всередині запиту?** — сигнатурна перевірка (WAF) на відомі
   патерни атак.
3. **Хто це, і що йому дозволено?** — перевірка особи та прав доступу.
4. **Чи не витікає нічого у відповіді, і чи нормальна поведінка з часом?**
   — захист від витоку даних та поведінковий аналіз.

Запит, відхилений на кроках 1–2, взагалі не потрапляє в каталог API — щоб
шум атак не засмічував карту реального API. Запит, що пройшов кроки 1–2,
записується в каталог незалежно від того, що станеться далі — включно з
пізнішим відхиленням на кроках 3–4.

## З чого складається система

- **Два порти, один процес.** Один порт для реального трафіку клієнтів,
  окремий — для керування/дашборду. Розділені навмисно: атака на перший не
  позбавляє доступу до другого.
- **Redis** — усе швидке й недовговічне: лічильники лімітів, чорні списки
  IP, поведінкові бали, сесії.
- **PostgreSQL (опційно)** — каталог API та журнал форензики. Без нього
  AEGIS працює як завжди, просто не веде довгостроковий каталог.
- **Конфіг оновлюється на льоту.** Зміна правил застосовується без
  перезапуску і без обриву активних з'єднань.
- **Мультитенантність.** Якщо систему використовують кілька клієнтів
  одночасно — їхні дані ізольовані, з додатковим запобіжником на рівні
  самої бази даних.

## Як це впроваджується

**Пакування:** один Docker-образ. Далі — вибір способу запуску:

- **Docker Compose** — один сервер, для демо чи першого пілоту. Просто,
  швидко перевірити на реальному трафіку без великих вкладень.
- **Kubernetes + Helm** — кілька копій за балансувальником,
  автомасштабування — стандарт для продакшн-інфраструктури.

**Розкатка йде поетапно**, щоб пілот не міг зламати клієнту прод:

1. **Observe** — тільки спостерігає й записує, нічого не блокує. Будує
   каталог API, показує, що було б відхилено.
2. **Tuning** — за зібраними даними прибираються хибні спрацювання.
3. **Enforcement** — вмикається реальне блокування та ліміти.
4. **Expansion** — той самий підхід розкатується на решту сервісів клієнта.
5. **Steady state** — далі робота за звітом: закриваємо те, що залишилось
   незахищеним.

## Де ми зараз

Продукт інженерно готовий і перевірений — контролі реально протестовані,
включно з поведінкою під час живих відмов інфраструктури. Що ще відкрито:
незалежна перевірка ззовні та перший пілот на реальному трафіку — обидва
зараз у роботі.
