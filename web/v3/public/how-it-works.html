01The problem

Modern APIs grow faster than anyone can keep track of by hand. Four structural gaps show up on almost every real system:

  • Forgotten endpoints. Shipped, never reviewed, never retired — nobody owns the decision.
  • Inconsistent protection. Every team configures auth and rate limits differently; "protected" means something different per service.
  • No consumer visibility. "Who calls this, and how much?" has no fast answer — the data is scattered across logs.
  • Silent data exposure. PII and payment data leak in responses unnoticed until someone reports it from outside.

AEGIS exists to be the one point that sees all of it, because all traffic passes through it.

02Why AEGIS

Normally this is three products from three vendors: an API Gateway (proxy, load balancing), a WAAP layer (firewall, rate limits, bot mitigation, DLP, identity), and an ASPM platform (catalog, risk, analytics). AEGIS is all three in one deployment — one place these three layers can't silently disagree with each other.

The differentiator isn't the firewall — everyone has a signature firewall. It's that AEGIS builds an API catalog and a "who calls what" graph from day one, and object-level leak detection is built directly on top of that graph (section 06). Most WAF-only competitors have no such foundation to build on.

AEGIS is self-hosted, no mandatory cloud. The only dependencies are Redis and PostgreSQL — infrastructure most companies already run. Nothing phones home.

Data plane for real traffic, admin plane for management — an attack on the first doesn't cut off the second.

Everything fast and short-lived: rate limits, IP blocklists, behavioral scores, sessions. Most keys carry a TTL.

API catalog and forensic log, fully async and off the request path. Without it, AEGIS still runs; it just doesn't keep a long-term catalog.
•
Config hot-reloads
A rule change takes effect without a restart and without dropping in-flight connections.

05Multi-tenancy

When several clients share one deployment, isolation runs on two layers, not one. Every Redis key is prefixed by tenant and every Postgres table carries tenant_id in a composite primary key — that's the layer that runs on every request. Underneath it, PostgreSQL itself enforces row-level security as a backstop, so a query that somehow forgets to scope by tenant gets zero rows back, not every tenant's rows.

06The flagship detector

A signature WAF cannot catch Broken Object Level Authorization (BOLA/IDOR) — a request for someone else's data by ID looks syntactically identical to a request for your own. AEGIS catches it two ways: bulk enumeration (many object IDs, fast, measured against a per-consumer learned baseline instead of one fixed number for everyone), and the harder case — a single wrong object ID with no volume pattern at all, caught by passively learning who owns what from real traffic and evaluating strictly after the response, on a 2xx only, so a backend's own 403/404 is never mistaken for a leak.

With a confirmed owner on record, a later cross-owner request to the same object is denied before it's forwarded — not just logged after the fact.

07Reliability posture

Not every control fails the same way when its backing store is unreachable, and that's deliberate. Rate limiting and IP reputation can be configured to deny everything on a Redis outage (fail-closed) — a defensible choice for a high-assurance deployment. Behavioral scoring has no such option; it's always fail-open, because denying every IP on the gateway during an infrastructure blip is a worse outcome than a temporary gap in one scoring signal.

This was measured, not just reasoned about: with Redis fully killed under sustained load, the data plane held 100% request success, latency bounded by fail-fast timeouts rather than hanging. Same result killing PostgreSQL under load — 100% success, flat latency — because catalog/forensic writes are fully decoupled from the request path.

08Deployment

Packaging is a single Docker image. Docker Compose for a demo or first pilot — one server, fast to validate on real traffic. Kubernetes + Helm for production — multiple replicas behind a load balancer, autoscaling, zero-downtime rolling updates.

Rollout is staged so a pilot can never break production traffic:

01
Observe
Watches and records, blocks nothing. Builds the catalog, shows what would've been rejected.
02
Tuning
False positives removed from collected data, per-route rules defined.
03
Enforcement
Real blocking, tuned rate limits, auth turned on where required.
04
Expansion
Same pattern rolled out to the rest of the estate.
05
Steady state
Ongoing work against the posture report — coverage up, shadow endpoints down.
