Łapanie IDOR-a, którego sygnaturowy WAF nie widzi

Pasywne wykrywanie własności obiektu na poziomie bramy — i dlaczego „oceniaj po odpowiedzi” jest tu całą sztuczką.

Weźmy najnudniejszą klasę podatności z OWASP API Top 10: Broken Object Level Authorization (BOLA), znaną też jako IDOR. Użytkownik zmienia liczbę w adresie URL —

GET /v1/orders/1001   → Państwa zamówienie
GET /v1/orders/1002   → czyjeś cudze, jeśli backend zapomniał sprawdzić

— i dostaje dane, które do niego nie należą. Żadnego wstrzyknięcia, żadnego zniekształconego ładunku, żadnej sztuczki z nagłówkiem. Żądanie jest składniowo bez zarzutu. Sygnaturowy WAF nie ma czego dopasować, bo nie ma żadnego wzorca. Dlatego BOLA pozostaje jednym z najczęstszych realnych naruszeń API lata po tym, jak je nazwano: klasa narzędzi, którą większość zespołów już ma (WAF, brama API, limiter), jest na nią strukturalnie ślepa.

AEGIS to brama bezpieczeństwa API działająca we własnej infrastrukturze. Ten tekst jest o jednym jej elemencie: jak wykrywamy wyciek pojedynczego obiektu pasywnie, na bramie, bez zbioru treningowego, bez sygnatury i — to część warta opisania — bez oznaczania normalnego przypadku, w którym autoryzacja już zadziałała.

Dwa różne błędy noszące tę samą nazwę

„Wykrywanie BOLA” zwykle oznacza jedną z dwóch bardzo różnych rzeczy, a ich mylenie jest miejscem, w którym większość naiwnych implementacji się myli.

Masowa enumeracja to przypadek łatwy: jeden konsument uderzający w /v1/orders/{id} dla tysiąca kolejnych identyfikatorów w minutę. To anomalia wolumenu — policz odrębne identyfikatory obiektów per konsument, per endpoint, w oknie i porównaj z progiem. My też to robimy, z adaptacyjną linią bazową per konsument zamiast stałej liczby (więcej o tym w osobnym tekście) — ale to nie jest ciekawa część.

Wyciek pojedynczego obiektu to przypadek trudny i ważniejszy: konsument żąda jednego obiektu, którego nie jest właścicielem, raz, bez żadnej sygnatury wolumenowej. Detektory enumeracji nie strzelają — nie ma enumeracji. To jest faktyczny kształt większości realnych incydentów IDOR: nie skrypt młócący kolejne identyfikatory, tylko jeden uwierzytelniony użytkownik, który raz spróbował sąsiedniego numeru.

Podejście: ucz się własności pasywnie, z ruchu, który już Państwo mają

Nie potrzeba do tego zbioru treningowego. Sygnał już jest: sam ruch Państwa API mówi, kto jest właścicielem czego — wystarczy chcieć go obserwować.

Mechanizm w zarysie:

  • Ucz się. Brama obserwuje udane żądania i dla każdego widzianego identyfikatora obiektu śledzi, który konsument (lub konsumenci) legalnie się do niego odwoływał.
  • Oznacz. Gdy do tego obiektu odwołuje się inny konsument — taki, który nigdy go nie dotykał i nie należy do dużej grupy dostępu współdzielonego — mamy kandydata na dostęp międzywłaścicielski.
  • Potwierdź, jeśli możesz. Jeśli ciało odpowiedzi API faktycznie nazywa właściciela (np. pole user_id), brama czyta je wprost i porównuje z tożsamością wywołującego. To zamienia heurystykę w potwierdzony fakt.
  • Blokuj po potwierdzeniu. Mając zapisanego potwierdzonego właściciela, późniejsze żądanie innego podmiotu do tego samego obiektu można odrzucić zanim trafi do Państwa backendu — a nie tylko zalogować po fakcie.

Nic z tego nie wymaga etykietowania danych ani trenowania modelu. Wymaga obserwowania prawdziwego ruchu i trzymania małej mapy właścicieli w Redisie z TTL.

Sztuczka, która naprawdę znaczy: oceniaj po odpowiedzi, wyłącznie przy 2xx

Oto rozróżnienie oddzielające detektor użyteczny od hałaśliwego. Oceńcie dostęp międzywłaścicielski zanim poznają Państwo odpowiedź backendu, a będą Państwo generować fałszywe alarmy bez przerwy — każde poprawnie autoryzowane żądanie, w którym backend słusznie zwraca 403 albo 404, wygląda z punktu widzenia bramy identycznie jak żądanie, które za chwilę się powiedzie.

Więc nie oceniajcie wcześniej. Oceniajcie później:

// Po odpowiedzi: potwierdź własność z ciała (jeśli OwnerFields jest
// skonfigurowane) albo wróć do heurystyki pierwszego odwołującego się.
// Oceniane po odpowiedzi, bo 2xx potwierdza, że obiekt faktycznie został
// zwrócony (4xx oznacza, że backend wyegzekwował autoryzację — to nie wyciek).
cw := &captureWriter{ResponseWriter: w, status: http.StatusOK}
next.ServeHTTP(cw, r)
if cw.status < 200 || cw.status >= 300 {
    return
}

4xx oznacza, że własna autoryzacja Państwa backendu już to złapała — poprawnie. Oznaczenie tego jako incydentu byłoby ponownym raportowaniem tego, że Państwa kontrola dostępu działa, czyli dokładnie tym rodzajem hałasu, przez który narzędzie bezpieczeństwa zostaje wyłączone w ciągu miesiąca. Z kolei 2xx na obiekcie należącym do kogoś innego oznacza, że obiekt naprawdę trafił do kogoś, kto nie powinien go mieć — prawdziwy wyciek, a nie „być może”.

Ta jedna decyzja o kolejności odpowiada za większość tego, że detektor jest użyteczny w praktyce, a nie tylko technicznie poprawny.

Własności nie obchodzi metoda HTTP

Jeden szczegół, który łatwo pomylić: tożsamość obiektu należy śledzić niezależnie od metody HTTP, mimo że wolumen enumeracji powinien być śledzony per metoda.

// bolaTarget rozstrzyga klucze BOLA dla żądania: endpoint zależny od metody
// ("METODA /szablon", używany do enumeracji), zakres obiektu NIEZALEŻNY od
// metody ("/szablon", używany do własności) oraz konkretne identyfikatory
// obiektów, do których nastąpił dostęp.
//
// Zakres obiektu celowo pomija metodę: zamówienie 1001 jest tym samym
// obiektem, czy jest czytane (GET), modyfikowane (PUT/PATCH), czy usuwane
// (DELETE), więc własność wyuczona z odczytu musi chronić je także przed
// zapisem przez kogoś innego.

Jeśli zakluczą Państwo własność konkretnie na GET /orders/{id}, napastnik, który nigdy obiektu nie przeczytał, ale wysyła do niego DELETE, przepływa prosto przez sprawdzenie własności, bo detektor nie ma zapisu dla tej metody. Zakluczenie własności samym obiektem, osobno od zastosowanego do niego czasownika, sprawia, że właściciel wyuczony z niewinnego odczytu chroni obiekt także przed zapisem przez kogoś innego, którego detektor nigdy wcześniej nie widział.

Identyfikator obiektu nie zawsze jest w adresie URL

Wszystko powyżej napisano w kategoriach segmentów ścieżki, bo taki kształt większość ludzi sobie wyobraża. Ale GraphQL całkowicie ten obraz rozbija: każda operacja idzie przez jeden endpoint, zwykle POST /graphql, a identyfikator obiektu mieszka w argumencie wewnątrz ciała żądania, a nie gdziekolwiek w URL-u.

POST /graphql
{"query": "query GetUser { user(id: 42) { ssn } }"}
// ścieżka to "/graphql" dla każdego żądania — identyfikator 42 jest w ciele

Detektor zakluczony wyłącznie na URL-u widzi jeden endpoint z nieskończonym ruchem i zerem identyfikatorów obiektów — co oznacza, że na API w GraphQL po cichu nie wykrywa niczego, wyglądając przy tym na zupełnie zdrowy. Dlatego AEGIS parsuje operację: argumenty o kształcie identyfikatora na każdym polu najwyższego poziomu stają się kandydatami na własność obiektu, zasilając dokładnie to samo śledzenie własności i enumeracji, które zasilałby segment ścieżki REST. Nic w opisanym wyżej detektorze się nie zmienia; zmienia się tylko miejsce, z którego czytany jest identyfikator.

Jedna subtelność warta wskazania: klucz śledzenia ma zakres po operacji i polu, a nie po samej nazwie pola. Dwa niepowiązane zapytania, które przypadkiem wystawiają pole o nazwie user, nie mogą dzielić jednego licznika enumeracji ani jednego zapisu własności — inaczej normalny ruch na jednym zapytaniu zatruwa linię bazową drugiego.

Ten sam parsing naprawia też odkrywanie: każda operacja staje się własnym wpisem katalogu, zamiast każdego wywołania GraphQL zapadającego się w jeden wiersz /graphql, a znalezisko z danymi osobowymi w odpowiedzi przypisuje się do operacji, która je zwróciła.

Czym to nie pretenduje być

Warto powiedzieć wprost o ograniczeniach, bo przechwalanie się detektorem jest sposobem, w jaki zespoły przestają mu ufać:

  • Bez skonfigurowanego owner_fields (mówiącego bramie, które pole odpowiedzi nazywa prawdziwego właściciela) działa to jako heurystyka — powinowactwo własności „pierwszego odwołującego się” — a nie potwierdzony fakt. Dokładnie dlatego jest oznaczane niższą wagą.
  • Zimny start. Pierwszy konsument dotykający świeżego obiektu jest uznawany za jego właściciela. Jeśli to założenie jest błędne, detektor jest w błędzie, dopóki ciało odpowiedzi nie powie inaczej.
  • Obiekty współdzielone. Niewielka liczba legalnych współwłaścicieli (wsparcie, wspólny zasób zespołu) wymaga albo listy dozwolonych, albo progu współdzielenia — inaczej będą Państwo oznaczać zwyczajny wspólny dostęp.
  • Parsing GraphQL kończy się na najwyższym poziomie. Jako identyfikatory obiektów czytane są tylko argumenty pól najwyższego poziomu operacji. Identyfikator pojawiający się wyłącznie w zagnieżdżonej selekcji albo osiągalny jedynie przez fragment nie jest dziś wydobywany — detektor raczej tam niedoraportowuje, niż błędnie przypisuje, ale niedoraportowuje.
  • To siatka bezpieczeństwa, a nie zastępstwo dla poprawnej autoryzacji w Państwa backendzie. Łapie to, co się prześliźnie — nie zastępuje sprawdzenia, które powinno było złapać to pierwsze.

Chcą Państwo sprawdzić, czy złapie coś realnego na Państwa własnym ruchu — bez dotykania produkcji? AEGIS ma tryb pasywny, który inspekcjonuje i zapisuje, ale niczego nie blokuje ani nie modyfikuje.
