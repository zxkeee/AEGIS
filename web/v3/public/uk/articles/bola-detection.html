Інженерія

Ловимо IDOR, якого сигнатурний WAF не бачить

Пасивне виявлення власності обʼєкта на рівні шлюзу — і чому «оцінюй після відповіді» тут і є весь фокус.

Візьмімо найнудніший клас вразливостей з OWASP API Top 10: Broken Object Level Authorization (BOLA), також відомий як IDOR. Користувач змінює число в адресі —

GET /v1/orders/1001   → ваше замовлення
GET /v1/orders/1002   → чуже, якщо бекенд забув перевірити

— і отримує дані, які йому не належать. Жодної інʼєкції, жодного спотвореного тіла, жодного трюку із заголовком. Запит синтаксично бездоганний. Сигнатурному WAF нема з чим звіряти, бо шаблону не існує. Саме тому BOLA лишається одним із найпоширеніших реальних зламів API через роки після того, як його назвали: клас інструментів, який більшість команд уже має (WAF, шлюз API, лімітер), структурно до нього сліпий.

AEGIS — це шлюз безпеки API, що працює у власній інфраструктурі. Цей текст про одну його частину: як ми виявляємо витік окремого обʼєкта пасивно, на шлюзі, без навчальної вибірки, без сигнатури і — ось частина, варта опису — не позначаючи нормальний випадок, коли авторизація вже спрацювала.

Дві різні помилки під однією назвою

«Виявлення BOLA» зазвичай означає одне з двох дуже різних явищ, і плутанина між ними — саме те місце, де помиляється більшість наївних реалізацій.

Масовий перебір — легкий випадок: один споживач бʼє в /v1/orders/{id} для тисячі послідовних ідентифікаторів за хвилину. Це аномалія обсягу: полічи різні ідентифікатори обʼєктів на споживача й на ендпоїнт у вікні та звір із порогом. Ми теж це робимо, з адаптивною базовою лінією на споживача замість фіксованої цифри (докладніше в окремому тексті) — але це не цікава частина.

Витік окремого обʼєкта — випадок складний, і саме він важить більше: споживач запитує один обʼєкт, яким не володіє, один раз, без жодної сигнатури обсягу. Детектори перебору не спрацьовують — перебору немає. Це і є справжня форма більшості реальних інцидентів IDOR: не скрипт, що молотить послідовні ідентифікатори, а один автентифікований користувач, який одного разу спробував сусідній номер.

Підхід: вчи власність пасивно, з трафіку, який у вас уже є

Навчальна вибірка для цього не потрібна. Сигнал уже є: сам трафік вашого API каже, хто чим володіє, — треба лише погодитись за ним спостерігати.

Механізм у загальних рисах:

  • Вчись. Шлюз спостерігає успішні запити і для кожного побаченого ідентифікатора обʼєкта відстежує, який споживач (чи споживачі) законно до нього звертався.
  • Познач. Коли до цього обʼєкта звертається інший споживач — той, хто ніколи його не торкався і не входить до великої групи спільного доступу, — це кандидат на доступ через межу власності.
  • Підтверди, якщо можеш. Якщо тіло відповіді API справді називає власника (скажімо, поле user_id), шлюз читає його прямо й порівнює з особою викликача. Це перетворює евристику на підтверджений факт.
  • Блокуй після підтвердження. Маючи записаного підтвердженого власника, пізніший запит іншої сторони до того самого обʼєкта можна відхилити перш ніж його передадуть вашому бекенду, а не лише залогувати постфактум.

Ніщо з цього не потребує розмічання даних чи навчання моделі. Потрібно спостерігати реальний трафік і тримати невелику карту власників у Redis із TTL.

Фокус, який справді важить: оцінюй після відповіді, лише на 2xx

Ось розрізнення, що відділяє придатний детектор від галасливого. Оцініть доступ через межу власності до того, як дізнаєтесь відповідь бекенда, — і будете безперервно породжувати хибні спрацювання: кожен правильно авторизований запит, де бекенд слушно повертає 403 чи 404, з погляду шлюзу виглядає так само, як запит, що от-от вдасться.

Тож не оцінюйте раніше. Оцінюйте пізніше:

// Після відповіді: підтвердь власність із тіла (якщо OwnerFields
// налаштовано) або повернись до евристики першого відвідувача.
// Оцінюється після відповіді, бо 2xx підтверджує, що обʼєкт справді
// повернули (4xx означає, що бекенд застосував авторизацію — це не витік).
cw := &captureWriter{ResponseWriter: w, status: http.StatusOK}
next.ServeHTTP(cw, r)
if cw.status < 200 || cw.status >= 300 {
    return
}

4xx означає, що власна авторизація вашого бекенда вже це впіймала — правильно. Позначити це як інцидент означало б удруге доповісти, що ваш контроль доступу працює, а це рівно той різновид шуму, через який інструмент безпеки вимикають упродовж місяця. Натомість 2xx на чужому обʼєкті означає, що обʼєкт справді віддали тому, хто не мав його отримати, — справжній витік, а не «можливо».

Це одне рішення про порядок і становить більшість того, чому детектор придатний на практиці, а не лише технічно коректний.

Власності байдуже до методу HTTP

Одна деталь, яку легко зробити навпаки: особу обʼєкта слід відстежувати незалежно від методу HTTP, хоча обсяг перебору треба відстежувати на метод.

// bolaTarget визначає ключі BOLA для запиту: залежний від методу ендпоїнт
// ("МЕТОД /шаблон", для перебору), НЕЗАЛЕЖНУ від методу область обʼєкта
// ("/шаблон", для власності) та конкретні ідентифікатори обʼєктів,
// до яких було звернення.
//
// Область обʼєкта навмисно опускає метод: замовлення 1001 є тим самим
// обʼєктом, чи його читають (GET), змінюють (PUT/PATCH), чи видаляють
// (DELETE), тож власність, вивчена з читання, має захищати його й від
// запису іншою стороною.

Якщо ключувати власність саме по GET /orders/{id}, нападник, який ніколи обʼєкт не читав, але шле до нього DELETE, пропливає просто крізь перевірку власності, бо в детектора немає запису для цього методу. Ключування власності самим обʼєктом, окремо від застосованого до нього дієслова, означає, що власник, вивчений з невинного читання, захищає обʼєкт і від запису іншою стороною, якого детектор ніколи раніше не бачив.

Ідентифікатор обʼєкта не завжди в адресі

Усе вище написано в термінах сегментів шляху, бо саме таку форму більшість уявляє. Але GraphQL цілком руйнує цю картину: кожна операція йде через один ендпоїнт, зазвичай POST /graphql, а ідентифікатор обʼєкта живе в аргументі всередині тіла запиту, а не будь-де в адресі.

POST /graphql
{"query": "query GetUser { user(id: 42) { ssn } }"}
// шлях — "/graphql" для кожного запиту, ідентифікатор 42 у тілі

Детектор, ключований лише на адресі, бачить один ендпоїнт із нескінченним трафіком і нулем ідентифікаторів обʼєктів — а отже на GraphQL-API він тихо не виявляє нічого, маючи при цьому цілком здоровий вигляд. Тому AEGIS розбирає операцію: аргументи у формі ідентифікатора на кожному полі верхнього рівня стають кандидатами на власність обʼєкта і живлять точно те саме відстеження власності й перебору, яке живив би сегмент шляху REST. Ніщо в описаному вище детекторі не змінюється; змінюється лише місце, звідки читається ідентифікатор.

Одна тонкість, варта згадки: ключ відстеження має область за операцією і полем, а не за самою назвою поля. Два непов'язані запити, які випадково виставляють поле з назвою user, не мають ділити один лічильник перебору чи один запис власності — інакше нормальний трафік одного запиту отруює базову лінію іншого.

Той самий розбір виправляє й виявлення: кожна операція стає власним записом каталогу, замість того щоб усі виклики GraphQL злипались в один рядок /graphql, а знахідка персональних даних у відповіді приписується операції, що її повернула.

Чим це не претендує бути

Варто прямо сказати про обмеження, бо перебільшувати можливості детектора — це спосіб, у який команди перестають йому довіряти:

  • Без налаштованого owner_fields (який каже шлюзу, яке поле відповіді називає справжнього власника) це працює як евристика — спорідненість власності «першого відвідувача», а не підтверджений факт. Саме тому воно позначається нижчою критичністю.
  • Холодний старт. Перший споживач, що торкнувся свіжого обʼєкта, вважається його власником. Якщо це припущення хибне, детектор хибить, доки тіло відповіді не скаже інакше.
  • Спільні обʼєкти. Невелика кількість законних співвласників (підтримка, спільний ресурс команди) потребує або списку дозволених, або порога спільного доступу — інакше ви позначатимете звичайний спільний доступ.
  • Розбір GraphQL зупиняється на верхньому рівні. Як ідентифікатори обʼєктів читаються лише аргументи полів верхнього рівня операції. Ідентифікатор, що зʼявляється винятково у вкладеній вибірці або досяжний лише через фрагмент, сьогодні не видобувається — детектор там радше недозвітує, ніж приписує хибно, але недозвітує.
  • Це страхувальна сітка, а не заміна правильної авторизації у вашому бекенді. Вона ловить те, що прослизнуло, — вона не замінює перевірку, яка мала впіймати це першою.

Хочете перевірити, чи впіймає воно щось реальне на вашому власному трафіку — не торкаючись продакшену? У AEGIS є пасивний режим, який інспектує й записує, але нічого не блокує й не змінює.
