Інженерія

Ми обмежуємо кожен запит орендарем. І все одно додали запобіжник на рівні бази

Код застосунку колись забуде речення WHERE. База даних, що застосовує ізоляцію сама, не забуває ніколи.

Ізоляція даних у багатоорендному середовищі має один добре відомий режим відмови, і він не екзотичний: хтось додає новий запит, новий ендпоїнт, новий звіт через півроку — і забуває речення WHERE tenant_id = ?. Кожна таблиця AEGIS уже несе tenant_id у складеному первинному ключі, і кожен запит у коді за ним фільтрує. Це необхідно. Саме собою цього не досить — бо воно залежить від того, щоб кожен майбутній рядок коду робив це правильно, назавжди, без другого рівня, який упіймає той один, що не зробив.

Тому є другий рівень. PostgreSQL здатен застосовувати ізоляцію орендарів сам, незалежно від того, чи застосунок згадав про це попросити.

Механізм: RLS, примусово

ALTER TABLE forensic_logs ENABLE ROW LEVEL SECURITY;
ALTER TABLE forensic_logs FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON forensic_logs
    USING (tenant_id = current_setting('app.tenant_id', true));

FORCE — це частина, яку легко пропустити і яка важить найбільше. Саме лише ENABLE ROW LEVEL SECURITY у PostgreSQL не застосовує політику до власника таблиці, а роль бази даних застосунку зазвичай і є цим власником. Отже непримусова політика — рівно той різновид захисту, який тихо не захищає єдине зʼєднання, що має значення. FORCE застосовує політику і до власника. Зʼєднання, яке не встановило явно, від імені якого орендаря воно діє, не отримує «всі рядки» випадково — воно отримує нуль рядків.

Проведення особи орендаря крізь транзакцію

Політика читає current_setting('app.tenant_id', true) — змінну сесії Postgres, а не значення стовпця, яке застосунок передає в запиті. Кожен шлях запису встановлює її явно, в межах транзакції:

// withTenantTx закріплює GUC через set_config(..., is_local=true), тож
// область орендаря ніколи не витікає між зʼєднаннями з пулу, між запитами

is_local=true важить саме тому, що зʼєднання беруться з пулу. Без нього налаштування, зроблене на зʼєднанні з пулу, могло б залишитись видимим наступному, непов'язаному запиту, який випадково використає те саме зʼєднання, — а це звело б нанівець увесь сенс. Обмеження транзакцією означає, що налаштування випаровується в мить завершення транзакції, незалежно від того, що зʼєднання робитиме далі.

Доведення напрямку fail-closed, а не лише заява про нього

Властивість, яка тут справді важить: що відбувається, коли область орендаря ніколи не встановлена — помилка, пропущений шлях коду, зʼєднання, що оминуло налаштування. Без тесту це рівно той сценарій, якого заява «fail closed» зазвичай не переживає. Тому він покритий прямо:

func TestPG_RLS_FailsClosedWithoutGUC(t *testing.T) {
    // необмежений SELECT — без жодного встановленого app.tenant_id — має повернути
    // нуль рядків, а не рядки всіх орендарів
}

func TestPG_RLS_RejectsCrossTenantWrite(t *testing.T) {
    // WITH CHECK у політиці має заблокувати INSERT/UPDATE, що намагається записати
    // під tenant_id, який не збігається з областю сесії
}

Перший тест важить найбільше, бо саме його наївна реалізація найчастіше перевертає. Легко побудувати обмеження орендарем, яке за відсутності області відмовляє відкрито — повертає все, бо ніщо не наказало інакше. Увесь сенс розміщення цього на рівні бази, а не лише в коді застосунку, у тому, що типова поведінка бази за відсутності будь-якої інструкції — показати нічого, а не все.

Одна експлуатаційна пастка, яку це саме виявляє

RLS має в Postgres добре відому пастку: роль із BYPASSRLS або з правами суперкористувача ігнорує безпеку на рівні рядків цілком, із FORCE чи без. Якщо роль бази даних застосунку колись отримає суперкористувача — під час інциденту, міграції, добронамірного «просто щоб швидко це продебажити» — запобіжник тихо перестає існувати: без помилки, без рядка в лозі, без жодного сигналу, що це сталося. Це рівно той різновид відмови, що невидимий до дня, коли починає важити, тож його загартовано явно: роль, що підключається, має NOSUPERUSER NOBYPASSRLS, а перевірка на старті гучно попереджає, якщо ця роль колись відійде від цього стану.

Чим це є і чим не є

  • Це запобіжник, а не основний механізм ізоляції. Обмеження на рівні застосунку (кожен ключ Redis із префіксом орендаря, кожен запит відфільтрований) усе одно працює на гарячому шляху. RLS ловить той день, коли в цьому обмеженні є помилка.
  • Воно не замінює розділення орендарів на рівні мережі, якщо ваша модель загроз потребує і цього — воно діє цілком усередині однієї спільної бази.
  • Воно має справжню, виміряну ціну: на практиці незначну. Навантажувальний тест зі змішаним трафіком кількох орендарів показав накладні витрати в межах шуму (373,6 → 375,7 RPS, p50 +0,6 мс) проти тієї самої конфігурації без нього.

Цікаво, як виглядає живий хаос-тест для рівнів нижче за цей — Redis і Postgres, убиті посеред трафіку, а не лише описані?
