01Проблема

Сучасні API ростуть швидше, ніж хтось здатен відстежувати вручну. Чотири структурні прогалини трапляються майже в кожній реальній системі:

  • Забуті ендпоїнти. Випущені, ніколи не переглянуті, ніколи не виведені з експлуатації — ніхто не володіє цим рішенням.
  • Непослідовний захист. Кожна команда налаштовує автентифікацію й ліміти по-своєму; «захищено» означає різне в кожному сервісі.
  • Немає видимості споживачів. На питання «хто це викликає і як часто?» немає швидкої відповіді — дані розкидані по логах.
  • Тихий витік даних. Персональні та платіжні дані витікають у відповідях непомітно, доки хтось ззовні не повідомить.

AEGIS існує, щоб бути єдиною точкою, яка бачить усе це — бо весь трафік проходить крізь нього.

02Навіщо AEGIS

Зазвичай це три продукти від трьох постачальників: API Gateway (проксі, балансування), рівень WAAP (фаєрвол, ліміти запитів, захист від ботів, DLP, особа) і платформа ASPM (каталог, ризик, аналітика). AEGIS — це всі три в одному розгортанні, одне місце, де ці три рівні не можуть тихо суперечити одне одному.

Відмінність не у фаєрволі — сигнатурний фаєрвол є в усіх. Відмінність у тому, що AEGIS від першого дня будує каталог API і граф «хто що викликає», а виявлення витоків на рівні обʼєкта побудоване просто поверх цього графа (розділ 06). У більшості конкурентів, що виросли з WAF, такої основи немає — а те, що є, зазвичай зупиняється на REST. AEGIS парсить і операції GraphQL, тож той самий граф і той самий детектор покривають обидва світи.

AEGIS self-hosted, і це суть, а не спосіб упакування. Salt, Noname, Imperva та Akamai постачають безпеку API як SaaS: їм потрібна копія вашого трафіку у їхній хмарі. Для банку під DORA, для лікарні чи державного органу це не вподобання, а поріг, який вони не можуть подолати. AEGIS — один бінарник мовою Go, на вашому залізі й вашій базі даних: без агентів, без sidecar-ів, без облікового запису в чужій хмарі, без звернень «додому». Єдині залежності — Redis і PostgreSQL, тобто інфраструктура, яку більшість компаній уже тримає.

Доказова частина випливає з того самого. Знахідки зіставляються з NIS2 (ст. 21 управління ризиками, ст. 23 строки сповіщень), DORA (ст. 8–10 та 17–19) і ISO 27001 Додаток A, через OWASP API Top 10. Звіти підписуються Ed25519 і перевіряються окремою утилітою, яка відмовляється працювати з ключем, узятим із того самого документа — аудитор перевіряє на власній машині, не довіряючи ані вам, ані нам.

04Інфраструктура

•
Два порти, один процес
Площина даних для робочого трафіку, адміністративна — для керування; атака на першу не відрізає другу.
•
Redis
Усе швидке й короткоживуче: ліміти запитів, списки заблокованих IP, поведінкові оцінки, сесії. Більшість ключів мають TTL.
•
PostgreSQL — необовʼязковий
Каталог API і криміналістичний журнал, повністю асинхронно й поза шляхом запиту. Без нього AEGIS усе одно працює; просто не веде довготривалого каталогу.
•
Конфігурація перезавантажується на ходу
Зміна правила діє без перезапуску й без розриву поточних зʼєднань.

05Багатоорендність

Коли кілька клієнтів ділять одне розгортання, ізоляція працює на двох рівнях, а не на одному. Кожен ключ Redis має префікс орендаря, а кожна таблиця Postgres несе tenant_id у складеному первинному ключі — це рівень, що працює на кожному запиті. Під ним сам PostgreSQL застосовує безпеку на рівні рядків як запобіжник, тож запит, який якимось чином забув обмежитись орендарем, отримує нуль рядків, а не рядки всіх орендарів.

06Флагманський детектор

Сигнатурний WAF не здатен упіймати Broken Object Level Authorization (BOLA/IDOR) — запит на чужі дані за ідентифікатором синтаксично виглядає так само, як запит на власні. AEGIS ловить це двома способами: масовий перебір (багато ідентифікаторів обʼєктів, швидко, зміряний проти вивченої базової лінії конкретного споживача, а не проти однієї фіксованої цифри для всіх) і складніший випадок — один хибний ідентифікатор без жодного шаблону обсягу, що виявляється через пасивне навчання з реального трафіку, хто чим володіє, і оцінку суворо після відповіді, лише на 2xx, щоб власні 403/404 бекенда ніколи не були прийняті за витік.

Коли підтверджений власник уже записаний, пізніший запит іншої сторони до того самого обʼєкта відхиляється до пересилання — а не лише журналюється постфактум.

Це стосується не лише REST. Тіло GraphQL — query GetUser { user(id: 42) { ssn } } — розбирається так само: аргумент у формі ідентифікатора на полі верхнього рівня стає кандидатом на власність обʼєкта точно так, як сегмент шляху чи поле тіла JSON, з областю за операцією і за полем, тож два непов'язані запити зі спільною назвою поля ніколи не ділять один лічильник. Той самий розбір живить пасивне виявлення (кожна операція — власний запис каталогу, а не один плаский кошик /graphql) і детект персональних даних (витік у відповіді GetUser приписується до GetUser, а не до «GraphQL» узагалі).

07Поведінка при відмові

Не кожен механізм відмовляє однаково, коли його сховище недосяжне, і це навмисно. Обмеження частоти та репутація IP можуть бути налаштовані так, щоб при відмові Redis відмовляти всьому (fail-closed) — обґрунтований вибір для розгортання з високими вимогами. У поведінкової оцінки такої опції немає; вона завжди fail-open, бо відмовляти кожній IP-адресі на шлюзі під час збою інфраструктури — гірший результат, ніж тимчасова прогалина в одному сигналі оцінки.

Це виміряно, а не лише обґрунтовано: із повністю вбитим Redis під тривалим навантаженням площина даних утримала 100% успішних запитів, а затримка була обмежена таймаутами, а не зависанням. Той самий результат із вбитим PostgreSQL під навантаженням — 100% успіху, рівна затримка — бо записи каталогу та криміналістичного журналу повністю відчеплені від шляху запиту.

08Розгортання

Пакування — один образ Docker. Docker Compose для демо чи першого пілота: один сервер, швидка перевірка на реальному трафіку. Kubernetes + Helm для продакшену: кілька реплік за балансувальником, автомасштабування, оновлення без простою.

Розгортання поетапне, щоб пілот ніколи не міг зламати робочий трафік — і перший етап узагалі не на шляху запиту:

01
Дзеркало
Ваш проксі надсилає копію кожного запиту; AEGIS ніколи не стоїть у розриві й ніколи не торкається відповіді. Зупиніть шлюз посеред пілота — трафік цього не помітить. Саме тут починається перша співпраця.
02
Спостереження
Уже inline, але нічого не блокує. Будує каталог, показує, що було б відхилено.
03
Налаштування
Хибні спрацювання прибрані за зібраними даними, правила визначені на маршрут.
04
Блокування
Справжнє блокування, налаштовані ліміти запитів, автентифікація увімкнена там, де потрібна.
05
Розширення
Той самий шаблон розгорнутий на решту середовища.
06
Сталий стан
Поточна робота за звітом стану — покриття вгору, тіньові ендпоїнти вниз.

09Фактичний стан

Побудовано й перевірено — і чесно щодо того, що лишається відкритим, без згладжування:

✓
Повний ланцюжок механізмів, звірений із джерелами
WAF, DLP, особа JWT, виявлення BOLA/BFLA, пасивне виявлення, багатоорендність — двадцять три middleware, кожен звірений із реальним кодом. Цей список подавав двадцять один, доки хтось не перелічив; бракувало ConsumerID і BehaviorProfile.
✓
REST і GraphQL однаково
BOLA, пасивне виявлення й приписування персональних даних розбирають операції GraphQL — той самий детектор і той самий каталог, один шлях коду для обох, а не окремий модуль GraphQL. Вкладені поля та фрагменти поки не обходяться.
✓
Перевірено хаосом, а не лише описано
Redis і PostgreSQL убиті наживо під тривалим навантаженням — 100% успіху обидва рази.
✓
Примус схеми
Відхиляє незадокументовані поля тіла за вашим контрактом OpenAPI — закриває mass assignment.
✓
Безпечна поведінка при відмові
Кожен механізм має задокументований, свідомий вибір fail-open або fail-closed — а не типове значення, яке ніхто не розглядав.
—
Зовнішній пентест
Ще не зроблений — незалежний аудит перед будь-якою заявою про готовність до продакшену.
—
Немає зовнішнього якоря для підписаних доказів
Печатки й реєстри живуть у власній базі клієнта, і ключ підпису належить йому — оператор, який його тримає, міг би переписати запис і підписати заново. Служба міток часу або журнал прозорості це закриває; вона не побудована.
—
Реальні розгортання
На живому робочому трафіку — і саме тут потрібен партнер для впровадження.
