We Killed Redis and Postgres Under Load, on Purpose

"Fails gracefully" is a claim. Here's what happened when we actually pulled the plug on both backing stores mid-traffic, with numbers, not adjectives.

Every security product's docs say some version of "designed for resilience." Almost none of them show the run where someone killed the database mid-request and recorded exactly what happened. This is that run, for both of AEGIS's backing stores, plus a rolling-update drain test that found a real bug and led to a real fix — which we're including because pretending the first attempt was clean would defeat the point of publishing this at all.

Redis: 50 req/s, killed mid-run

Redis backs rate limiting and IP reputation on the hot path. Both are configured fail-open by default (see the companion post on why that's a deliberate choice for some controls and not others). Redis was killed completely, mid-traffic, at 50 requests/sec sustained.

Redis up100%~tens of ms
Redis fully down100%864 ms, max 1.30s
Recovered100%back to 42ms

Zero failed requests through the entire outage. The elevated latency isn't the fail-open logic being slow — it's the Redis client hitting its own fail-fast timeouts (1s dial, 500ms read/write, one retry) before falling through, instead of hanging on the multi-second defaults an unconfigured client would sit on per request.

PostgreSQL: 100 req/s, killed mid-run

Postgres backs the API catalog and forensic log — reads and writes to it are meant to be off the request path entirely. This is the run that actually tests whether that's true rather than just documented.

Before (PG up)4498100.0%7 / 10 / 11 ms
PG fully down2000100.0%7 / 10 / 11 ms
Recovered2500100.0%7 / 10 / 11 ms

The data plane genuinely does not notice. Latency doesn't even move — because the catalog worker and forensic sink are async by design, decoupled from the proxied request, not just documented as decoupled. The admin-side GET /api/catalog read (a separate, non-hot-path endpoint) did fail for the outage window and recovered the instant Postgres came back, with no operator action needed.

What this run actually found, and the fix: during the outage, that admin catalog read was returning HTTP 500 instead of 503. That's a real bug this test surfaced — 500 reads as "this endpoint is broken," 503 correctly tells a load balancer or client "a dependency is down, back off and retry." Fixed by classifying connection-level errors and returning 503 specifically for backing-store unavailability across the admin read endpoints, with a regression test (TestStoreUnavailable_Classifies) so it can't quietly regress.

Rolling updates: the first attempt shed a full burst of connection errors

Separately from database failure: what happens to in-flight traffic during a normal, planned rolling deployment? 100 req/s, SIGTERM sent to the gateway mid-traffic, requests classified as ok / 5xx / connection error.

Before a fix: Go's default Shutdown closes the listener immediately on SIGTERM. Zero requests came back as 5xx — but every single one of the 1200 requests sent during the drain window came back as a connection error, refused outright, because /readyz was still reporting healthy right up until the listener slammed shut. A real load balancer hasn't yet noticed the instance is going away and keeps routing to it anyway. Every rollout was shedding a full burst of connection errors — not a bug in the traditional sense, just the default behavior nobody had pointed a chaos test at yet.

The fix — a lame-duck grace period: on SIGTERM, flip /readyz to 503 first, keep serving established connections for a configured grace window, then close the listener.

Phasenok5xxconn errors
Before fix — drain window1200001200
After fix — drain window12006010599

601 requests that would have been refused now complete instead, during the window a real load balancer needs to notice /readyz went unhealthy and stop routing new traffic. The remaining connection errors in that window are traffic sent after the grace period elapsed and the process actually exited — which a correctly readiness-gated load balancer wouldn't be sending by then. This is what "zero-downtime rollout" needs to actually mean: not zero errors in a vacuum, zero errors given a load balancer that respects readiness.

The honesty part

This run was on macOS with Docker Desktop — backing services in containers, gateway as a host binary. It validates behavior (does the data plane survive an outage, does the drain actually shed connection errors correctly) — it is explicitly not a capacity benchmark. The Docker Desktop VM adds scheduling overhead that makes absolute throughput numbers meaningless to publish. A dedicated-hardware run for real capacity numbers is separate, outstanding work — we'd rather say that plainly than let a behavior test quietly stand in for a capacity claim it was never designed to make.
