The One Control That Has No Fail-Closed Option

Rate limiting and IP reputation can be configured to deny everything when Redis is down. Behavioral scoring can't be — there's no config field for it. That's deliberate, not an oversight.

"Fail open or fail closed" is usually presented as a single global choice a security product makes once. It shouldn't be. Different controls protect against different things, and the right failure direction for one is often the wrong one for another running in the same request path.

Two controls, same outage, opposite right answer

Redis goes down. Every control that reads from it has to decide what to do about a request it can no longer check.

Rate limiting and IP reputation — RateLimit.FailClosed, IPGuard.FailClosed — are real config fields an operator can set to true. If the backing store that enforces them is gone, deny the request. That's a defensible default for a high-assurance deployment: better to serve nothing than to serve everything unmetered and unfiltered during an outage.

Behavioral scoring is different. There's no Behavior.FailClosed field anywhere in the config schema. It's not that the default is false and you can flip it — the option doesn't exist. Every request that would have been scored is simply scored, and if the score calculation can't reach its data, the practical result is a request that gets treated as unscored rather than as guilty by default.

Why deny-by-default is the wrong call specifically here

Behavioral scoring accumulates risk across a history of requests from an IP — it's inherently a control about patterns over time, not about any single request. Set it to fail closed and a Redis outage means every IP on the gateway, including every legitimate one with a spotless history, starts being denied purely because the system can no longer read a history it would otherwise have vouched for them. You'd be converting an infrastructure outage into a total traffic outage, for a control whose entire job is nuance ("is this IP's pattern unusual"), not a binary allow/deny gate.

Rate limiting and IP reputation don't have this problem in the same way — they're closer to a hard cap and a static-ish list, either of which failing closed degrades gracefully into "temporarily more restrictive," not "block everyone regardless of history."

What the code actually does when the store is unreachable

// Step 1: check score from prior history BEFORE serving the request.
score := st.CalcBehaviorScore(r.Context(), ip, cfg.ScoreThreshold)
if score >= cfg.ScoreThreshold {
    // ... block ...
}

There's no error branch here that denies the request. A score that can't be computed doesn't get treated as maximally suspicious — it doesn't clear the threshold, so the request proceeds. This is the concrete shape of "intentionally fail-open": not a missing error handler, a present one that's designed to not escalate to a block.

This isn't a theoretical claim — it's a measured one

Talk is cheap for failure-mode claims, so this was run against a live instance under sustained traffic with Redis killed mid-test, not just reasoned about:

ConditionResult
Redis fully down, 50 req/s sustained100% request success
Latency during outagep99 864 ms, max 1.30 s
Latency after recoveryp99 back to 42 ms

The elevated latency during the outage isn't scoring logic slowing down — it's the store client hitting its fail-fast timeouts (1s dial, 500ms read/write, one retry) before falling through to the fail-open path, instead of hanging for the multi-second default a naive Redis client would sit on per request.

The honest tradeoff, stated plainly

This means during a Redis outage, behavioral auto-banning is effectively paused — an IP that would have been flagged and banned mid-outage isn't, until the store comes back. That's a real gap, not a hidden one. It's also, we think, obviously the better failure mode than the alternative: a scoring gap during a rare infrastructure incident, versus every legitimate user on the gateway getting denied because the system that was supposed to vouch for their good history couldn't be reached.
