The Order Is Load-Bearing

Why a security gateway's middleware order is part of its contract — and a diagram mistake we made ourselves, caught, and are writing up instead of quietly fixing.

Every request through AEGIS passes through roughly twenty middleware stages before it reaches your backend. The obvious question anyone asks when they see a list that long is "does the order matter, or is that just how it happened to get written?" It matters — enough that we pin the order with a named-step test that fails CI if anyone reorders it without meaning to. Three examples of why.

Identity must resolve before anything trusts it

TenantResolve runs first, full stop, because everything downstream — rate limits, blocklists, the catalog — reads the tenant from context. Put it anywhere else and every control behind it is scoping decisions against a tenant it hasn't determined yet.

CleanHeaders runs second, immediately after, and strips any client-supplied X-Gateway-* or X-JA3-* header before a single downstream control has a chance to read — and trust — a value the client could have forged. Run this later and you've spent however many stages came before it trusting headers nobody has verified yet.

Discovery sits in a very specific place, and it's not arbitrary

The catalog-building middleware sits after rate-limiting, bot detection, and the WAF, but before authentication and DLP. Both boundaries are deliberate, for opposite reasons:

  • After the early filters, so a request already rejected as an attack — blocked by the WAF, rate-limited, flagged as a bot — never reaches the catalog at all. Attack noise doesn't get to pollute the map of your real API surface.
  • Before auth and DLP, so the observation it records still reflects whatever those later stages decide — including a rejection. A request that clears the early filters is recorded regardless of what auth or DLP do to it afterward.

Authorization-abuse detection needs verified roles to exist first

BOLA/BFLA detection runs after JWT authentication for a reason that sounds obvious once stated and is easy to get backwards under time pressure: it reads the caller's roles to decide whether a privileged path was accessed without permission. Run it before authentication and there are no verified roles yet to check against — the detector would either have nothing to evaluate or, worse, trust unverified claims.

The part we're not going to quietly fix

An earlier draft of one of our own explainer diagrams — not this site, an internal one — showed identity ("who is this?") as the first gate a request passes, ahead of rate-limiting and the WAF. That's backwards from the actual chain, and we caught it by going back to the source file instead of trusting our own prior summary of it. The corrected, verified order is what's described above — rate and reputation first, then content inspection, then identity, then data-leak and behavior checks last.

We're mentioning this specifically, not editing it away silently, because it's the exact failure mode this whole post is about: a description of the order drifting from the order that's actually enforced, and nobody noticing until someone checks the source instead of the summary.

The object-ownership detector that runs in this chain — after auth, evaluated after the response — has its own writeup.
