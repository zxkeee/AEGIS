Catching the IDOR a Signature WAF Can't See

Passive, gateway-level object-ownership detection — and why "evaluate after the response" is the whole trick.

Take the most boring vulnerability class in the OWASP API Top 10: Broken Object Level Authorization (BOLA), also known as IDOR. A user changes a number in a URL —

GET /v1/orders/1001   → your order
GET /v1/orders/1002   → someone else's order, if the backend forgot to check

— and gets data that isn't theirs. No injection, no malformed payload, no header trick. The request is syntactically perfect. A signature-based WAF has nothing to pattern-match against, because there is no pattern. This is why BOLA remains one of the most common real-world API breaches years after it was named: the class of tool most teams already run (WAF, API gateway, rate limiter) is structurally blind to it.

AEGIS is a self-hosted API security gateway. This post is about one piece of it: how we detect a single-object leak passively, at the gateway, without a training set, without a signature, and — this is the part worth writing about — without flagging the normal case where authorization already worked.

Two different bugs wearing the same name

"BOLA detection" usually means one of two very different things, and conflating them is where most naive implementations go wrong.

Bulk enumeration is the easy case: one consumer hitting /v1/orders/{id} for a thousand sequential IDs in a minute. That's a volume anomaly — count distinct object IDs per consumer per endpoint in a window, compare against a threshold. We do this too, with an adaptive per-consumer baseline instead of a fixed number (more on that in a separate post) — but this part isn't the interesting bit.

The single-object leak is the hard case, and it's the one that matters more: a consumer requests one object it doesn't own, once, with no volume signature at all. Enumeration detectors don't fire — there's no enumeration. This is the actual shape of most real IDOR incidents: not a script hammering sequential IDs, just one authenticated user who happened to try a neighboring ID once.

The approach: learn ownership passively, from traffic you already have

You don't need a training set for this. You already have the signal: your API traffic itself tells you who owns what, as long as you're willing to watch it.

The mechanism, roughly:

  • Learn. The gateway watches successful requests and, for each object ID it sees, tracks which consumer(s) have legitimately accessed it.
  • Flag. When a different consumer accesses that object — one who has never touched it before, and who isn't part of a large shared-access group — that's a candidate cross-owner access.
  • Confirm, if you can. If the API's response body actually names the owner (a user_id field, say), the gateway reads it directly and compares it against the caller's identity. This turns a heuristic into a confirmed fact.
  • Block, once confirmed. With a confirmed owner on record, a later cross-owner request to the same object can be denied before it's forwarded to your backend — not just logged after the fact.

None of this requires labeling data or training a model. It requires watching real traffic and keeping a small owner map in Redis with a TTL.

The trick that actually matters: evaluate after the response, on 2xx only

Here's the discriminator that separates a usable detector from a noisy one. Evaluate cross-owner access before you know the backend's answer, and you'll generate false positives constantly — every properly-authorized request where the backend correctly returns a 403 or 404 looks identical, from the gateway's point of view, to a request about to succeed.

So don't evaluate before. Evaluate after:

// Post-response: confirm ownership from the body (if OwnerFields is
// configured) or fall back to the first-accessor heuristic. Evaluated
// after the response so a 2xx confirms the object was actually returned
// (a 4xx means the backend enforced authorization — not a leak).
cw := &captureWriter{ResponseWriter: w, status: http.StatusOK}
next.ServeHTTP(cw, r)
if cw.status < 200 || cw.status >= 300 {
    return
}

A 4xx means your backend's own authorization already caught it — correctly. Flagging that as an incident would just be re-reporting your backend's own access control working, which is exactly the kind of noise that gets a security tool disabled within a month. A 2xx on a cross-owner object, on the other hand, means the object was actually returned to someone who shouldn't have it — a real leak, not a maybe.

This single ordering decision is most of what makes the detector usable in practice instead of just technically correct.

Ownership doesn't care about HTTP method

One detail that's easy to get wrong: object identity should be tracked independent of the HTTP method, even though enumeration volume should be tracked per-method.

// bolaTarget resolves the BOLA keys for a request: the method-specific
// endpoint ("METHOD /template", used for enumeration), the method-
// INDEPENDENT object scope ("/template", used for ownership), and the
// concrete object IDs accessed.
//
// The object scope omits the method on purpose: order 1001 is the same
// object whether it is read (GET), modified (PUT/PATCH) or deleted
// (DELETE), so ownership learned from a read must also protect it
// against a cross-owner write.

If you key ownership by GET /orders/{id} specifically, an attacker who has never read an object but sends a DELETE to it sails straight through your ownership check, because the detector has no record for that method. Keying ownership by the object itself, separately from the verb applied to it, means an owner learned from an innocuous read also protects the object against a cross-owner write it's never seen before.

The object ID isn't always in the URL

Everything above is written in terms of path segments, because that's the shape most people picture. But GraphQL breaks that picture completely: every operation goes through one endpoint, usually POST /graphql, and the object ID lives in an argument inside the request body rather than anywhere in the URL.

POST /graphql
{"query": "query GetUser { user(id: 42) { ssn } }"}
// path is "/graphql" for every request — the ID 42 is in the body

A detector keyed purely on the URL sees one endpoint with infinite traffic and no object IDs at all — which means, on a GraphQL API, it silently detects nothing while looking perfectly healthy. So AEGIS parses the operation: the id-shaped arguments on each top-level field become object-ownership candidates, feeding the exact same ownership and enumeration tracking a REST path segment would. Nothing about the detector above changes; only where the ID is read from.

One subtlety worth calling out: the tracking key is scoped by operation and field, not by field name alone. Two unrelated queries that both happen to expose a field called user must not share one enumeration counter or one ownership record — otherwise normal traffic on one query poisons the baseline for the other.

The same parse also fixes discovery: each operation becomes its own catalog entry instead of every GraphQL call collapsing into a single /graphql row, and a PII finding in a response attributes to the operation that returned it.

What this doesn't claim to be

Worth being direct about the limits, since overclaiming a detector is how teams stop trusting it:

  • Without a configured owner_fields (telling the gateway which response field names the true owner), this runs as a heuristic — "first accessor" ownership affinity — not a confirmed fact. It's flagged at a lower severity for exactly that reason.
  • Cold start. The first consumer to touch a fresh object is assumed to be its owner. If that assumption is wrong, the detector is wrong until the response body confirms otherwise.
  • Shared objects. A small number of legitimate co-owners (support staff, a shared team resource) needs either an allowlist or a shared-object threshold, or you'll flag ordinary shared access.
  • GraphQL parsing stops at the top level. Only the arguments on an operation's top-level fields are read as object IDs. An ID that appears solely inside a nested selection, or one reachable only through a fragment spread, is not extracted today — the detector under-reports there rather than misattributing, but it does under-report.
  • This is a safety net, not a substitute for your backend doing authorization correctly. It catches what slips through — it doesn't replace the check that should have caught it first.
