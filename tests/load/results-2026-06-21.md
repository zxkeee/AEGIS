# AEGIS load benchmark — 2026-06-21

First on-hardware run after MT phases 1–6 are merged. Establishes the
multi-tenant overhead and confirms RLS does not regress throughput.

## Environment

| | |
|---|---|
| Date | 2026-06-21 |
| Gateway image | `aegis-gateway:demo` (sha256:8b4188...) — includes RLS, IAM, MT phases 1–6 |
| Backend | `kennethreitz/httpbin` over the docker `aegis-demo-net` bridge |
| Redis | `aegis-demo-redis` (`requirepass`), `aegis-demo-net` bridge |
| PostgreSQL | `aegis-postgres` 15-alpine, role `aegis` hardened `NOSUPERUSER NOBYPASSRLS` |
| Host | Debian NUC, Docker 29.5.3, LAN gigabit; client runs on macOS over Wi-Fi |
| Load tool | k6 v2.0.0 |
| Load shape | 20 VUs, 15s steady state; `requests: 1_000_000` so rate-limit is out of the picture |

Numbers below include Wi-Fi RTT between the laptop and the home server. The
*absolute* p95/p99 should be read in that light; the *delta* between the
single-tenant and multi-tenant runs is the meaningful figure.

## Results

### Single-tenant baseline (`gateway_load.js`)

| | |
|---|---|
| Throughput | **373.6 req/s** |
| p50 | **33.46 ms** |
| p95 | **103.74 ms** |
| Errors | 0.00 % |

### Multi-tenant, 3 tenants (`multitenant_load.js`)

| | |
|---|---|
| Throughput | **375.7 req/s** |
| p50 (aggregate) | **34.05 ms** |
| p95 (aggregate) | **103.64 ms** |
| Per-tenant p50 | acme 34.77 / globex 32.93 / initech 34.46 ms |
| Per-tenant p95 | acme 104.82 / globex 101.34 / initech 104.23 ms |

### Multi-tenant + 10 % attack mix (`multitenant_load.js -e ATTACK=0.10`)

| | |
|---|---|
| Throughput | **1508.7 req/s** |
| p50 (aggregate) | **7.89 ms** |
| p95 (aggregate) | **13.61 ms** |
| Attack requests blocked | 4407 / ~4527 (≈ 97 %, rest 429-ed) |

## Reading

- **Multi-tenant overhead is in the noise.** 373.6 → 375.7 RPS (+0.6 %),
  p50 +0.6 ms, p95 essentially identical. The extra cost of phase 2–3
  isolation (`WHERE tenant_id` + RLS policy evaluation + `gw:t:<tenant>:` key
  prefixes) does not show up at this VU count. RLS in particular sits inside
  the same transaction that already issues the `WHERE` filter, so the planner
  has the same access pattern in both runs.
- **WAF blocks are cheap.** When 10 % of traffic is a SQLi payload, the
  aggregate p50 collapses from ~34 ms to ~8 ms — the WAF rejects them
  early in the chain, before the proxy is called, so blocked requests are
  much shorter than passed ones. This is the desired behaviour.
- **Per-tenant latency is balanced.** No tenant pays a noticeably higher
  cost than its peers; the policy / prefix scheme does not favour the
  alphabetically first tenant by accident.

## Reproducing

```bash
# Bench gateway with rate-limit lifted (so 20 VUs from one IP don't hit it).
ssh fitness@192.168.31.116 'docker exec aegis-demo-gateway sh -c \
  "sed -e s/requests: 30/requests: 1000000/ -e s|listen: .8080.|listen: \\\":8090\\\"| -e s|admin_listen: .8081.|admin_listen: \\\":8091\\\"| config/gateway.demo.yaml > /tmp/bench.yaml"'
ssh fitness@192.168.31.116 'docker cp aegis-demo-gateway:/tmp/bench.yaml /tmp/aegis-bench.yaml'
ssh fitness@192.168.31.116 'docker run -d --name aegis-bench-gateway \
  --network aegis-demo-net \
  -e AEGIS_ADMIN_SECRET=... -e AEGIS_REDIS_PASSWORD=... -e AEGIS_FORENSIC_DSN=... \
  -p 192.168.31.116:8090:8090 -p 192.168.31.116:8091:8091 \
  -v /tmp/aegis-bench.yaml:/app/config/gateway.bench.yaml \
  aegis-gateway:demo --config config/gateway.bench.yaml'

k6 run -e TARGET=http://192.168.31.116:8090 -e PATH=/get -e VUS=20 -e DURATION=15s tests/load/gateway_load.js
k6 run -e TARGET=http://192.168.31.116:8090 -e PATH=/get -e VUS=20 -e DURATION=15s tests/load/multitenant_load.js
k6 run -e TARGET=http://192.168.31.116:8090 -e PATH=/get -e VUS=20 -e DURATION=15s -e ATTACK=0.10 tests/load/multitenant_load.js
```
